# Module 06: Building & Testing a Live RAG Application Under Test (AUT)

## 1. The SDET Paradigm Shift: Testing Live Systems vs. Static Strings

In Days 1 through 4, we used static, hardcoded `actual_output` strings to learn the mathematical mechanics of DeepEval metrics. In software engineering terms, that was **Evaluator Unit Testing** (testing the test framework itself).

In real enterprise teams, an SDET tests an actual **System Under Test (SUT)**.

| Attribute | Static Prompt Testing (Days 1–4) | Live Application Testing (Day 5+) |
| :--- | :--- | :--- |
| **Source of `actual_output`** | Hardcoded Python string. | **Dynamic output** generated in real-time by the application service. |
| **Source of `retrieval_context`** | Hardcoded list of sentences. | **Live document chunks** fetched by the search engine / Vector DB. |
| **Test Value** | Verifies metric rubrics work. | **Catches real prompt regressions, model drift, and retrieval failures.** |
| **CI/CD Role** | Educational verification. | **Blocks PRs if a developer modifies `src/` and degrades quality.** |

## 2. Architecture of the Application Under Test (`src/`)

Our repository now separates application logic from test automation:

```
deep-eval-project/
├── src/                                  # 🚀 The Application Under Test (AUT)
│   ├── knowledge_base/
│   │   └── store_policies.json           # Realistic company policy documents
│   └── bot.py                            # CustomerSupportRAGBot class
│
└── tests/                                # 🧪 The SDET Automated Test Suite
    ├── test_04_live_rag_e2e.py           # Live E2E tests querying the bot
```

### The 3 Core Components of `src/bot.py`:

1. **The Knowledge Base (`store_policies.json`)**:
   Contains corporate policies for returns, hardware warranties, shipping speeds, lost packages, and VIP memberships.

2. **The Retriever (`retrieve()`)**:
   Searches the knowledge base and extracts the top $k$ most relevant document chunks based on the user's inquiry.

3. **The Generator (`query()`)**:
   Injects the retrieved documents into an empathetic persona prompt ("Nova") and calls Google Gemini, returning a structured `BotResponse(answer, retrieved_chunks, model_used)`.

## 3. The Live Pytest Automation Pattern

Instead of mocking or hardcoding responses, our test suite queries the live bot and feeds the dynamic response directly into DeepEval:

```python
import pytest
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric
from src.bot import CustomerSupportRAGBot


@pytest.fixture(scope="session")
def live_bot():
    """Initializes the live CustomerSupportRAGBot session."""
    return CustomerSupportRAGBot()


def test_live_bot_return_policy_inquiry(live_bot):
    user_query = "What is the return window for electronics?"

    # 1. Query the live application service
    response = live_bot.query(user_query)

    # 2. Wrap the live response into LLMTestCase dynamically
    test_case = LLMTestCase(
        input=user_query,
        actual_output=response.answer,             # Real text generated by Gemini
        retrieval_context=response.retrieved_chunks # Real documents retrieved
    )

    # 3. Assert live performance against quality thresholds
    assert_test(test_case, [
        AnswerRelevancyMetric(threshold=0.7),
        FaithfulnessMetric(threshold=0.8)
    ])
```

---

## 4. Why This Pattern is Crucial for CI/CD

If an AI engineer on your team:
- Edits the prompt template in `src/bot.py`
- Changes the temperature or model version
- Alters chunking in `store_policies.json`

Running `uv run pytest tests/test_04_live_rag_e2e.py` will automatically test the new live application output, identify any hallucinations or missing facts, and fail the build before bad code reaches production.
